### 关键发现（重要，复用价值高）
1. **云函数 rdb() 身份 = anon 角色**，JWT claims 仅 `{aud, exp, iat, iss, role:"anon"}`，**无 `sub`**
2. **用户 token（匿名 REST /auth/v1/signin/anonymously 或 js-sdk 登录）都带 `sub`** → 用 `claims->>'sub' IS NULL AND claims->>'role'='anon'` 作 RLS policy 可精确区分云函数与外部匿名
3. REST 匿名 token 与 js-sdk 匿名 token 的 claims 不同（前者有 sub/is_anonymous/user_metadata，后者有 client_type/scope）——**不要用 client_type 做判据**（REST token 没有）
4. **`*_view` 视图是第二条泄漏路径**：视图以 owner（表 owner，绕过 RLS）执行，anon 有 SELECT 即可读全表 → 已 REVOKE anon
5. 探测手段：SQL 函数 `current_setting('request.jwt.claims', true)::json` + 云函数 `rdb.rpc()`；REST 侧可用 `POST /v1/rdb/rest/rpc/<fn>`
6. identity 列（identity='d'）在 information_schema.columns 的 column_default 显示 NULL，实际有内建自增；序列名保留建表时的中文表名（客户列表_Id_seq 等），**批量导入显式 Id 不推进序列**，需 `setval(pg_get_serial_sequence(...), max+1, false)`
7. migration runner 身份非表 owner（报 42501），DDL 用 `execute + allowDdlViaExecute=true`（以 cloudbase_admin owner 身份执行）
